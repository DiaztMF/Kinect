Performance teardown · Enuma / Kinect

Kinect Frame Budget

The scanner streams from a 30 Hz sensor but was spending 1113 ms per frame — 0.9 FPS. Profiling found 89% of it inside a single Open3D call, and a second, quieter problem: the WebSocket re-sent the entire map every frame, so cost grew with scan length. Both are now fixed. The pose composition was also inverted, which is the part that mattered most for the actual 3D output.

01

How the sensor actually produces depth

The Kinect v1 is not a time-of-flight camera and not a stereo camera. It is a structured-light sensor built on the PrimeSense PS1080. An 830 nm laser diode fires through a diffractive optical element that splits the beam into a fixed, pseudo-random speckle pattern. An IR camera sitting 7.5 cm to the side photographs that pattern, correlates each local patch against a reference image memorised at a known calibration distance, and reads off the horizontal shift. Shift is disparity; disparity triangulates to range.

Three consequences fall straight out of that and every design decision downstream answers to them.

Error grows with the square of distance

Disparity resolves to a fixed fraction of a pixel, but range is inversely proportional to disparity, so the depth step widens quadratically. Inverting libfreenect's own raw–to–metre fit gives the exact size of one 11-bit quantisation step:

z(raw) = 1 / (3.3309495161 - 0.0030711016 × raw) raw ∈ [0, 2046], 2047 = no reading

This is why max_depth = 3.5 is the right call and why a single uniform voxel size across the whole range is a compromise: near the sensor the voxel throws away real precision, far from it the voxel is finer than the data justifies. Keeping the cut-off where the step size crosses the voxel size is the honest place to draw the line.

The intrinsics are only correct because of the mode

The driver selects freenect_find_depth_mode(MEDIUM, REGISTERED), which asks the sensor to warp depth into the RGB camera's frame and hand it back in millimetres. That is why fx = fy = 525, cx = 320, cy = 240 is right: those are the colour camera's parameters. Switching to FREENECT_DEPTH_MM would silently invalidate them — unregistered depth needs the IR camera's intrinsics instead (fx ≈ 594.2), and using the wrong set skews every reconstruction into a subtle shear that is very hard to spot by eye.

USB 2.0 is the hard ceiling

640×480 depth plus 640×480 Bayer colour at 30 Hz consumes roughly half of a USB 2.0 bus in isochronous transfers, which is why one sensor per host controller is the practical limit and why the event pump has to be drained continuously. Whatever the pipeline does per frame, 33.3 ms is the floor. Anything faster is re-processing a frame the sensor has not refreshed.

02

The canonical RGB-D scanner, and where this one sat

Every dense RGB-D reconstruction system since KinectFusion (Newcombe et al., 2011) is the same five stages. What separates them is which stage they invest in: KinectFusion put everything into frame-to-model tracking against a raycast TSDF; ElasticFusion swapped the volume for deformable surfels to get loop closure; Open3D's own reconstruction system cuts the sequence into fragments and runs multiway pose-graph optimisation over them.

The architectural finding is at stage 3. The app already builds a TSDF volume every frame — and then never tracks against it. Frame-to-frame odometry accumulates drift linearly with frame count and has no mechanism to ever recover it; frame-to-model odometry registers each new frame against a raycast of the fused volume, which averages out per-frame noise and holds the map rigid. The volume is already there. Using it for tracking is the largest accuracy upgrade still available, and it costs no new data structure.

Stage 2 being empty is the second gap. Raw Kinect depth has speckle holes at every surface discontinuity and along every shadow cast by the 7.5 cm baseline. Feeding it to the odometry unfiltered means the solver spends iterations fitting noise.

03

What the profiler found

Measured on the mock sensor so every stage sees identical input, 60 frames, warm. The headline is the first row: Open3D's legacy compute_rgbd_odometry is a single-threaded scalar implementation, and at full 640×480 with the default [20, 10, 5] iteration schedule it alone ate 89% of the frame.

The bandwidth problem was worse than the CPU one

Every frame packed the whole accumulated map into a binary buffer and pushed it down the socket. The browser then walked it point by point through a DataView, allocated two fresh Float32Arrays, and set React state — a full re-render and a full GPU re-upload, 20 times a second, over a buffer that never stops growing.

At 90 000 points that is 1.4 MB per frame, 28 MB/s sustained. A two-minute room scan would have taken it well past what a browser tab survives. The cost scaled with how long you had been scanning, which is the worst shape a hot loop can have.

04

What changed

Odometry moved to the Open3D tensor API

o3d.t.pipelines.odometry.rgbd_odometry_multi_scale is the vectorised, parallel implementation of the same hybrid objective. At full resolution it is 48 ms against the legacy 990 ms — identical transforms, 21× the speed. Tracking now runs at 320×240, which is standard practice and costs nothing in accuracy on a pyramid solver.

990 → 25 ms

A constant-velocity prior seeds each solve

The previous frame's accepted transform is handed to the solver as its initial guess instead of the identity. Under real hand motion this is most of the answer already, so the solver converges in fewer iterations and is far less likely to fall into a local minimum during a fast pan.

accuracy

The global map became a sorted voxel-key index

World points quantise to a packed int64 voxel key; a searchsorted against the sorted key array says which are new, and only those are stored. This replaces the per-frame voxel_down_sample and the periodic re-downsample of the whole map, and it hands the streaming layer its delta for free. Merging into a one-million-point map costs 3 ms.

66 → 5 ms

TSDF integration is keyframe-gated

The volume is only integrated when the camera has moved 4 cm or rotated 4° since the last integration. A static camera used to hammer the same voxels 30 times a second, which burned 23 ms a frame and over-weighted whatever it happened to be pointing at.

23 → 2.3 ms

The stream sends deltas, the browser appends

An 8-byte header carries the point count and a mode flag — append, or replace for a reconnecting client's full resync. The browser de-interleaves only the new points into preallocated typed arrays and issues a partial GPU upload of the range it just wrote, then advances drawRange. No reallocation, no full re-upload, and the point data never touches React state.

896 → 11 KB

Duplicate frames are skipped

The driver now exposes a monotonic frame counter bumped by the depth callback, and the stream loop refuses to re-run SLAM on a frame the sensor has not refreshed. At the old 0.9 FPS this could not happen; at 20 FPS against a 30 Hz sensor it would have doubled TSDF weights on every stall.

correctness

Importing the server no longer opens the sensor

A module-level app = get_default_app() ran on any import, so the test suite was opening the physical Kinect and flooding stderr with USB resync errors. It is built lazily now; uvicorn backend.server:app still works.

bug

Tilt acknowledgements report reality

The motor clamps to ±27°, but the acknowledgement echoed the requested angle and put that integer in a field the UI read as a boolean. It now returns the angle actually applied alongside the request.

bug
05

The bug that mattered most

Speed was the ask, but the reconstruction had a sign error in it, and no amount of throughput fixes a map built backwards.

compute_rgbd_odometry(prev, curr) returns the transform that maps points from the previous camera frame into the current one — Tcurr←prev. The camera-to-world pose therefore advances by its inverse. The code composed the raw transform instead:

- self.current_pose = self.current_pose @ trans + self.current_pose = self.current_pose @ np.linalg.inv(trans)

Every frame was placed at the mirror image of where the camera actually moved. Walking forward pushed the map backward; the reconstruction did not just drift, it folded in on itself, and the drift it did accumulate was doubled.

Regression test added

The mock sensor renders a static world from a camera on a known path, which makes it ground truth. The new test correlates the estimated pose translation against that path on all three axes and requires corr > 0.9. With the fix it measures +0.997 / +0.998 / +0.996; with the old composition, the same test measures −0.997 / −0.998 / −0.996 — a perfect mirror, which is exactly the signature of the bug.

06

Where the ceiling is now

49 ms against a 33 ms sensor period means the pipeline consumes roughly two of every three frames. Half of what remains is the odometry solve and most of the rest is memory traffic preparing the frame. In rough order of payoff:

  • Track against the model, not the last frame. Raycast the existing TSDF at the predicted pose and register the incoming frame against that. Same cost class as today's solve, and it is the difference between drift that grows without bound and drift that stays bounded. The volume is already being maintained.
  • Precondition the depth map. A bilateral filter before tracking is cheap and removes the speckle the solver currently spends iterations fitting.
  • Overlap capture with processing. Frame N's SLAM and frame N+1's capture are independent; running them concurrently would hide most of the 14 ms preparation cost behind the USB wait.
  • Scale the voxel with range. Section 01 shows the quantisation step crossing the map voxel size around 2 m. A voxel that widens with depth would stop storing far-field points at a precision the sensor cannot deliver.
  • A CUDA build is a drop-in. The tracker and the fusion path are already on the tensor API, so a GPU-enabled Open3D moves them to the device with a Device("CUDA:0") change and nothing else.
